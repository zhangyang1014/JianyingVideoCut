# 如何设计一个 Agent

## Agent 标准内容清单

设计任何 Agent 时，至少明确以下 8 项：

| 模块 | 要解决的问题 | 举例 |
| --- | --- | --- |
| 任务定义 | Agent 到底要完成什么 | 修复 Bug、生成报告、分析数据 |
| 上下文设计 | Agent 需要知道什么 | 用户信息、历史对话、项目规则 |
| 工具设计 | Agent 能调用什么能力 | 查数据库、读写文件、跑测试 |
| 权限控制 | Agent 什么不能做 | 不能删数据、不能泄露隐私 |
| 验证机制 | 怎么判断做得对不对 | 单元测试、合规检测、LLM Judge |
| 运行监控 | 出错后怎么追踪 | Trace、日志、版本记录 |
| 反馈迭代 | 怎么越用越好 | 失败样本库、Prompt 迭代 |
| 成功标准 | 如何验证做对了 | validation contract、task_status |

## 7 个工程模块

```
Agentic Engineering = Agent + Tool + Context + Eval + Guardrail + Human-in-the-loop + Data Loop
```

1. **Agent**：核心推理与行动 loop。
2. **Tool**：可调用的外部能力。
3. **Context**：注入 LLM 的信息（memory、state、RAG）。
4. **Eval**：评测体系，验证输出质量。
5. **Guardrail**：护栏规则，限制行为边界。
6. **Human-in-the-loop**：人工审批和升级。
7. **Data Loop**：从运行数据中提取改进信号。

## 设计检查清单

- [ ] 目标是否一句话能说清？
- [ ] 输入上下文是否明确？
- [ ] 工具列表是否最小且职责清晰？
- [ ] 禁止行为是否写进 prompt 和代码？
- [ ] 输出格式是否结构化（JSON / schema）？
- [ ] 是否有 Trace 记录？
- [ ] 成功标准是否可验证？
- [ ] 失败时是否有纠偏机制？
- [ ] 高风险动作是否需要人工审批？

## 什么时候值得用 Agent

值得用 Agent 的条件：

- 任务路径不确定，需要根据观察动态调整。
- 需要多工具调用和复杂 SOP。
- 有明确的边界和结果判断标准。
- 随着 agent 能力进化，计划可以持续优化。

不值得用 Agent 的条件：

- 逻辑完全确定，普通代码更可靠。
- 只需单次 LLM 调用。
- 没有工具调用需求。
